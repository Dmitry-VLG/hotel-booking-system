# Подтверждение резерва и компенсация

Решение: HELD имеет TTL а COMMITTED не истекает автоматически. Добавлен внутренний commit. Глобальных XA-транзакций нет.

При неизвестном результате HTTP применяется повтор той же идемпотентной команды либо безопасная отмена с release. До прояснения результата другой номер не выбирается.

release сохраняет терминальную запись даже если hold ещё не пришёл. Это предотвращает оживление позднего запроса. Восстановитель после дедлайна отменяет PENDING и повторяет освобождение; успешный сценарий заново не запускается.

timesBooked учитывает успешные подтверждения. Пользовательская отмена сохраняет историю; компенсация незавершённой саги убирает её вклад один раз.

## Однозначный отказ и неизвестный исход

HotelClient отличает структурированный бизнес-отказ Hotel (400/404/409 с соответствующим ApiError) от ответа прокси или неясного сетевого исхода. Если предыдущая попытка того же вызова завершилась тайм-аутом либо 5xx, последующий отказ не считается доказательством отсутствия резерва.

Подтверждённый отказ hold фиксируется локально как HOLD_REJECTED. Отмена такой операции не требует release и получает compensationStatus=NONE. Если отмена произошла конкурентно раньше ответа, подтверждённый отказ завершает уже назначенную компенсацию без повторов.

Для release произвольный HTTP 404 не является терминальным успехом: это может быть неверный маршрут или утрата состояния Hotel. Успех подтверждается корректным ответом RELEASED с совпадающими bookingId, reservationId, roomId и датами. Неоднозначный результат остаётся REQUIRED и видим в API и логах. Простое ограничение количества попыток не должно скрывать оставшийся резерв.

Статусы, фазы саги и состояния компенсации представлены enum; в БД сохраняются строковые значения, формат внешнего JSON сохранён.
