# Система бронирования отелей

Учебный REST API на Java 21, Spring Boot 3.5 и Spring Cloud 2025.0.
Позволяет искать свободные номера, создавать и отменять бронирования, управлять каталогом и пользователями. Работа с приложением выполняется через HTTP-запросы или Swagger UI.

## Структура проекта

| Модуль | Порт | Назначение |
| --- | --- | --- |
| `discovery-server` | 8761 | Реестр сервисов Eureka |
| `api-gateway` | 8080 | Внешняя точка входа и маршрутизация запросов |
| `booking-service` | 8081 | Пользователи, авторизация и бронирования |
| `hotel-service` | 8082 | Отели, номера и календарь резервов |
| `common` | — | Общие DTO, обработка ошибок и компоненты безопасности |

Booking и Hotel используют отдельные базы H2. Сервисы обнаруживают друг друга через Eureka. Внутренний API Hotel недоступен через Gateway.

## Подготовка и запуск

Требуются JDK 21 и Maven 3.9.

В IntelliJ IDEA выберите JDK 21 для проекта, импортирования и запуска Maven, а также для конфигураций запуска приложений. Эти настройки не меняют Java во встроенном терминале: команды ниже должны выполняться с JDK 21. Для этого достаточно один раз настроить системные `JAVA_HOME` и `PATH` и перезапустить IDE.

Из корня проекта создайте локальную пару ключей и выполните сборку с тестами:

```powershell
java .\tools\GenerateKeys.java
mvn clean verify
```

Ключи создаются в `keys/private.pem` и `keys/public.pem`. Повторно генерировать существующую пару не нужно; инструмент откажется перезаписывать файлы.

Настройте переменные окружения в терминале или конфигурации запуска соответствующего приложения:

| Переменная | Приложения | Значение |
| --- | --- | --- |
| `PUBLIC_KEY` | Gateway, Booking, Hotel | Абсолютный `file:` URI файла `keys/public.pem` |
| `PRIVATE_KEY` | Booking | Абсолютный `file:` URI файла `keys/private.pem` |
| `DEMO_ENABLED` | Booking, Hotel | `true` для загрузки демонстрационных данных |
| `DEMO_ADMIN_PASSWORD` | Booking при включённых демоданных | Пароль пользователя `admin` |
| `DEMO_USER_PASSWORD` | Booking при включённых демоданных | Общий пароль пользователей `alice` и `bob` |

Демонстрационные пароли должны содержать не менее 8 символов и занимать не более 72 байт UTF-8. Ключи, действующие пароли и токены не публикуйте в репозитории.

Запускайте JAR-файлы из `target` каждого модуля в отдельных терминалах: сначала `discovery-server`, затем `hotel-service`, `booking-service` и `api-gateway`. Переменные окружения задаются отдельно для каждого терминала. Точные команды приведены в [инструкции по запуску](docs/manual.md).

После запуска проверьте:

- [Eureka](http://127.0.0.1:8761): зарегистрированы `API-GATEWAY`, `BOOKING-SERVICE` и `HOTEL-SERVICE` со статусом `UP`.
- [Состояние Gateway](http://127.0.0.1:8080/actuator/health): ответ содержит `"status": "UP"`.

Для остановки нажмите `Ctrl+C` в каждом терминале приложения.

## API

Внешний адрес: `http://127.0.0.1:8080`.

| Возможность | Методы и пути |
| --- | --- |
| Регистрация и вход | `POST /api/auth/register`, `POST /api/auth/login` |
| Отели | `GET`, `POST /api/hotels`; `GET`, `PATCH`, `DELETE /api/hotels/{id}` |
| Номера | `GET`, `POST /api/rooms`; `GET`, `PATCH`, `DELETE /api/rooms/{id}` |
| Рекомендации | `GET /api/rooms/recommend` |
| Создание брони и история | `POST`, `GET /api/bookings` |
| Просмотр и отмена брони | `GET`, `DELETE /api/bookings/{id}` |
| Управление пользователями | `GET`, `POST /api/users`; `GET`, `PATCH`, `DELETE /api/users/{id}` |
| Все номера и статистика | `GET /api/admin/rooms`, `GET /api/admin/statistics/occupancy` |

Изменение каталога, управление пользователями и пути `/api/admin/**` требуют роли `ADMIN`. Пользователь работает только со своими бронированиями; владелец определяется по JWT.

После входа передавайте `accessToken` в заголовке `Authorization: Bearer <accessToken>`. Пользовательский JWT действует один час, затем требуется повторный вход. Gateway и бизнес-сервисы проверяют токен независимо.

Поиск свободных номеров требует `startDate` и `endDate` в формате `YYYY-MM-DD`. Дата заезда включается в период, дата выезда не включается. Поле `available` обозначает возможность эксплуатации номера; занятость на выбранные даты определяется по резервам. Рекомендации сортируются по `timesBooked`, затем по `id`.

Создание брони требует заголовок `Idempotency-Key`. При `autoSelect=true` нужен `hotelId`, а `roomId` игнорируется. При ручном выборе нужен `roomId`.

Основные ответы об ошибках: `401` — отсутствующий, недействительный или просроченный токен; `403` — недостаточно прав; `404` — ресурс не найден, в том числе при запросе чужой брони; `409` — конфликт доступности или повторное использование ключа с другим содержимым запроса.

- [Booking Service](http://127.0.0.1:8081/swagger-ui/index.html)
- [Hotel Service](http://127.0.0.1:8082/swagger-ui/index.html)

## Согласованность бронирования

Booking сохраняет `PENDING` и вызывает `hold`, затем `commit` в Hotel. После успеха бронь становится `CONFIRMED`. При ошибке выполняются отмена и `release`; неудачное освобождение повторяет фоновый процесс. Локальные транзакции БД не удерживаются во время HTTP-вызовов.

Ключ идемпотентности уникален в пределах пользователя. Повтор завершённого POST с тем же ключом и содержимым возвращает исходный результат; для незавершённой операции возможен ответ `202`. Текущее состояние брони запрашивается через GET, включая состояние после отмены.

`timesBooked` учитывает успешные подтверждения. Пользовательская отмена сохраняет этот счётчик; компенсация незавершённой операции убирает её вклад однократно. События и ошибки связываются по `traceId`, `bookingId` и `reservationId`.

## Проверки и ограничения

`mvn test` запускает тесты, а `mvn clean verify` выполняет сборку и проверки всех модулей. Конкурентный тест Hotel использует настоящую H2; тесты Booking моделируют ответы Hotel. Сквозные ручные сценарии и результаты вынесены в документацию ниже.

Данные H2 хранятся в памяти и теряются после остановки соответствующего приложения. При сбросе демонстрационной системы обе бизнес-БД следует очищать согласованно. Несколько независимых экземпляров Hotel с отдельными H2 не образуют общий календарь. Spring Boot 3.5 выбран по учебному заданию; постоянное хранение и промышленное развёртывание выходят за рамки этой реализации.
